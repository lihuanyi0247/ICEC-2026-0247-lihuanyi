# 记录 03｜文件名只到"分"，按名字排序会把 25 段录音的标签全贴错

**日期**：2026-11-18
**一句话结论**：这是一个**不会报错的错误** —— 脚本不崩、日志干净、
准确率掉到 50% 像个"算法不行"的问题，但根因是标签从一开始就贴错了。

---

## 背景

项目三的录音命名规则是 `<设备>_<工况>_<会话>_<序号>.wav`。
手机自己录出来的文件名是 `录音机-20261118-2330.wav` 这种，
需要批量改名，把 25 个无意义的名字映射成
`FAN_S0_S1_01.wav` … `FAN_O1_S1_05.wav`。

映射的依据是**录制顺序**：S0 五段 → N1 五段 → N2 五段 → F1 五段 → O1 五段。

---

## AI 给的第一版方案是错的

它说"按文件名排序就行"，因为文件名里带时间戳。

**实际情况**：手机文件名只精确到**分钟**。
10 秒左右一段，一分钟能录 4~5 段，于是同一分钟内会出现：

```
录音机-20261118-2330.wav
录音机-20261118-2330(1).wav
录音机-20261118-2330(2).wav
...
录音机-20261118-2330(10).wav
```

按字符串排序的结果是：

```
...2330.wav → ...2330(1).wav → ...2330(10).wav → ...2330(2).wav → ...
```

**(10) 排在了 (2) 前面。** 一旦跨过 10 段，顺序就乱了，
工况标签从第 11 段开始整体错位。

## 为什么这个错误特别危险

| 好错误 | 这个错误 |
|---|---|
| 脚本崩、报错 | 脚本正常跑完 |
| 日志里有 traceback | 日志里全是 `[√] 25/25 通过` |
| 立刻发现 | 要等训练完看准确率才发现 |
| 一看就知道哪里错 | 看准确率低，会去怀疑特征、怀疑模型、怀疑录音质量 |

**它会把你引到完全错误的排查方向上。** 如果只有 2~3 个文件的顺序错，
准确率只掉几个点，几乎不可能被发现 —— 而这些错标的数据会永久留在训练集里。

## 我怎么验证的

不看文件名，看**文件系统的修改时间**：

```powershell
Get-ChildItem D:\录音\S1 -Filter *.wav | Select-Object Name, LastWriteTime
```

`录音机-20261118-2317.wav` 的修改时间是 `23:17:23`，
创建时间是 `23:18:17`（后者是拷进电脑的时刻）。
→ **数据线拷贝保留了手机的原始写入时间，而且精确到秒。**

所以正确的排序键是 `mtime`，不是文件名。

## 但 mtime 也有一个坑

如果文件经过微信 / QQ 传输，**mtime 会被重置成接收时间**。
25 个文件的时间会挤在几秒内 —— 这时候按 mtime 排序等于随机排序，
错误比按文件名更彻底。

**所以加了第二道闸门**：如果 25 个文件的时间跨度 < 60 秒，
直接拒绝执行，并提示"这批文件的时间不可信，请用数据线重新拷"。

实测：正常拷贝跨度 1446 秒 → 不告警；人为把时间改成同一秒 → 立即告警。

## 最后怎么解决

`rename_recordings.py` 的排序逻辑：

```python
files = sorted(glob(wav), key=lambda p: p.stat().st_mtime)   # 按秒级 mtime
span = files[-1].stat().st_mtime - files[0].stat().st_mtime
if span < 60:
    sys.exit("时间跨度只有 %.0fs，八成被传输工具重置过，先用数据线重拷" % span)
```

再加两道保护：
1. **默认 dry-run**，只打印 25 行预览，加 `--apply` 才动文件
2. **源扩展名与目标不一致时拒绝执行** —— 把 `m4a` 改名成 `.wav`
   会得到一个读不了的假 WAV，必须显式加 `--convert` 才真转码

## 复盘

- **"不报错的错误"比"报错的错误"贵得多。** 凡是自动化批量处理，
  都应该在中间加一步"人能看一眼的预览"。
- 排序键要选**语义上正确**的那个：录制顺序 → 录制时间 → 文件名。
  文件名是给人看的，不是给程序用的。
- 这类问题以后可以直接拿去当面试素材：**它同时展示了"会怀疑自己"
  和"能在没有报错的情况下找到错在哪"两件事。**
