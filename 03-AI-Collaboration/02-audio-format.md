# 记录 02｜24 bit 录音"读不了"：错的是我的检查工具，不是录音

**日期**：2026-11-18
**协作对象**：WorkBuddy（AI 助手）
**一句话结论**：我把"工具不支持"当成了"数据不合格"，差点让 75 段录音白重录一遍。
真正的错误不在录音，在检查脚本自己。

---

## 背景

项目三要求 `5 工况 × 15 组` 原始 WAV。我打算先录 10 秒试一段，
确认格式对了再录全程 —— 因为格式设错要重录 75 段，这个成本差 100 倍。

用手机自带「录音机」录了一段，跑预检脚本：

```
录音机-20261118-2306.wav
读不了：不支持的位深 24 bit
```

**我的提问（原文）**：
> 这样录的能用吗（附报错截图）

---

## AI 说错的地方

AI 的第一反应是"手机录音格式不对，需要改设置或者用 ffmpeg 转码"。
方向错了 —— 手机录音机**根本没有位深/声道开关**，我翻遍了设置也没有。
是**检查脚本**读不了 24 bit，不是录音有问题。

## 我怎么验证的

不看报错文案，直接用 Python 打文件的 RIFF 头：

```python
import wave
w = wave.open(path)
print(w.getnchannels(), w.getframerate(), w.getsampwidth()*8)
```

输出 `2 48000 24` —— 24 bit / 48 kHz / 双声道，是**完全合法**的 PCM WAV，
标准库 `wave` 也能正常打开读取帧数据。

那为什么脚本报错？因为脚本自己写了一句：

```python
if sampwidth not in (1, 2):
    raise ValueError("不支持的位深 %d bit" % (sampwidth * 8))
```

**它只支持 8 bit 和 16 bit，遇到 3 字节（24 bit）就主动抛错。**
这是我（或者说 AI 帮我写的时候）埋的一行防御性代码，
把"我没想到的格式"当成了"错误格式"。

## 最后怎么解决

不去适配手机，而是让脚本读得懂 24 bit。要点是**不能一个点一个点地算**：

```python
# 24 bit = 3 字节，按三个字节拼成整数
tri = b[i:i+3]
v = tri[0] | (tri[1] << 8) | (tri[2] << 16)
if v >= 1 << 23:      # 补符号位
    v -= 1 << 24
# 左移 8 位搬进 32 bit 量程（数值 ×256，满量程同步放大，全是比值所以结论不变）
v <<= 8
```

一段 10 秒 48 kHz 的录音有 **~96 万个采样点**，
纯 Python 逐点循环要跑好几秒；用 `int.from_bytes` / `array` 批量处理才可接受。

**验证转换无损**：原始 24 bit 直读和转出的 16 bit 文件，
谱质心都是 **183 Hz** —— 一致，说明降位深没有改变声音特征。

## 另一个关键判断：把"不合格"拆成两类

原来的脚本把所有异常都判"不合格"，导致**明明能用的文件报错**。
改成两类之后才合理：

| 类别 | 含义 | 例子 |
|---|---|---|
| 【不合格】必须重录 | 数据本身错了，转码救不回来 | 削波、近静音、太短、采样率过低 |
| 【提示】导入时自动修 | 只是格式不规范，内容没问题 | 24 bit、双声道、DC 偏置、峰值贴 0 疑 AGC |

这条区分直接决定了明天的动作：**24 bit 不用重录**，
导入时用 ffmpeg 输出 `pcm_s16le / mono / 44100`，
源文件（24 bit 母版）不删不搬，留在原处 —— 溯源时可以出示母版。

实测：25 份真实 24 bit 录音 **74.7 MB → 22.9 MB（31%）**，工况分布 5×5 正确。

## 复盘

**报错文案会误导人。** "不支持的位深"读起来像"你的文件有问题"，
但它真实的含义是"我的代码没写这个分支"。
以后看到类似的报错，先分清是**数据错**还是**工具能力边界**。

第二个收获：**先写预检，再批量采集。** 花 20 分钟试录 10 秒，
省掉了 75 段重录的风险。这个顺序以后所有采集类任务都该照做。
